# 日报生成与披露策略

输入：各来源当天信号（日历、邮件、Agent 对话、本地文件）+ `config.json`。输出：内部分享安全、**充实且能体现工作分量**的日报草稿。

## 1. 合并信号

同一事项往往在多个来源出现（一场会 = 日历事件 + 会前材料 + 会后邮件）。按事项合并，不按来源罗列。每个事项记录：主题、所属工作范围、证据来源、事实状态。

## 2. 事实状态（宁可保守，不可虚报）

| 状态 | 写法 | 需要的证据 |
|---|---|---|
| `done` | 「完成…」 | 用户明确确认 / 会议纪要或转写 / 会后决定与 follow-up / 已发送的成果邮件 |
| `ongoing` | 「推进…」 | 已结束的日历事件 + 对应材料；当天有实质修改的工作文件 |
| `planned` | 「计划…」 | 未来日历、待办、会前材料。绝不能写成已完成 |
| `blocked` | 「等待…（通用表述）」 | 明确的阻塞信号；不写敏感细节 |

- 不以文件名机械判断状态：`xx-prep.md` 只是弱证据。综合正文语义、时间顺序、已结束日历、后续动作推断。
- 多个信号一致指向已发生时可直接写，不必逐条追问用户；证据不足一律降级为 `ongoing`/`planned`。
- 不虚构会议、参与人、决策、交付物、指标或结果。可以写真实存在的计划块，但计划就是计划。
- 状态不等于新动作：来源仅写「初稿，尚未评审」，只能保留这个状态，不能改写成「我主动标记未评审」「我阻止下游推进」。主动语态不能创造贡献。
- 同一事项的状态、意义和下一步放在同一条，不能拆成额外工作条目；只有一件有证据的事就写一条。

## 3. 充实化演绎（向上管理写法）

日报的目标读者是管理者。一句话流水账（「转发了一份文件」）既不体现工作量，也不体现判断力。每条事项按下面的公式展开成 2-3 句，**从事实向外演绎，但演绎必须停在证据的边界内**：

**叙事公式**：`[事项名]：做了什么（拆解真实动作）→ 当前状态/下一步 → 为什么重要（挂在具体事实上）`

**演绎阶梯**（每一句话都要能归到某一级）：

| 级别 | 可以写 | 例子 |
|---|---|---|
| A 直接证据 | 信号里明确存在的动作与事实 | 「转交外部律师审阅并列明审阅重点」 |
| B 有据拆解 | 仅展开来源明确记录的子动作，不根据职业惯例推断已经做过 | 转发文件并列出 3 项审阅重点 → 「已转交文件，附上 3 项待审阅问题」；不能补写通读附件 |
| C 意义与影响 | 该事项对基金/流程/风险的客观意义，不涉他人反应 | 「供外部审阅时核对程序与授权范围」；目的不能写成已实现的效果 |
| ✗ 禁止 | 没有证据的新事件、他人的反应评价、结果数字、未发生的成果 | ✗「律师认为质量很高」✗「为基金挽回损失」 |

**分量框架**（每天选 1-2 条重点事项给足篇幅，其余从简）：

- 把动作放进流程坐标：「交割收尾」「签署前把关」「风险前置」——读者立刻明白这件事处在哪个环节、为什么现在做。
- 量化只用真实可数的数字：几家企业、几份文件、几项审阅重点、从多少封往来中筛出几条线索。数字必须可复核。
- 体现判断力：写出「筛掉了什么、为什么不跟进」和「主动确认/推动了什么」，这比罗列动作更显专业。
- 框架词（风险把控、推进闭环、保障节奏）必须挂在具体事实上，一条里最多一个；堆砌空话比流水账更糟。

**长度目标**：信号充足时全文 400-800 字；证据少时允许短于 400 字，不为凑篇幅补动作、指标或成果；重点事项 3-4 句（含过程颗粒：环节区分、时间压缩、判断依据），次要事项 1 句；超过 800 字先删形容词再删次要条目。

### 金字塔三规则（明托，逐条硬约束）

1. **结论先行，概括句开头**。「今日主线」必须是概括当天各条推进的**观点句**，回答「今天整体推进到哪了」；每条重点事项的第一句写「行动的结果 + 流程坐标」，支撑动作放后面。**禁用缺乏思想句**：「今天做了 3 件事」「处理了一些邮件」「参与了若干会议」「推进了各项工作」——只报类别不报观点的句子一律重写。
2. **措辞明确到能想象出画面、能检验做没做成**。模糊 → 明确（投资场景对照）：
   | 模糊（❌） | 明确（✔） |
   |---|---|
   | 跟进了交割 | 收齐二期交割签署版文件并核对要素，确认原件寄送安排 |
   | 处理董事会文件 | 通读决议及附件，整理出 3 项审阅重点转外部律师 |
   | 看了一些新项目 | 从当日 10+ 封往来中筛出 1 条值得评估的线索，其余不跟进 |
3. **归组排序**。同一事项的多源信号合并成一条；条目按重要性降序；超过 5 条先归类（投前/投后/基金事务等，相互独立不重叠）再在组内排序。找不到排序逻辑的条目，多半不该单列。

**重点事项可用微型 SCQA 句式**（背景/冲突 → 行动 → 下一步）：「X 交割进入收尾环节（背景），今日收到签署版文件包（行动），核对后只待纸质件归档（下一步）」。「风险与关注」栏天然是冲突位：写真实依赖，不渲染。

### 分量放大器（同样的事实讲到满分）

事实层由 §2 证据规则锁死；本节解决的是**呈现层**：多数人把 100 分的工作讲成 50 分——被动语态藏起自己、判断被写成杂务、成果埋在句尾。以下规则把真实工作讲出全部分量，仍不新增任何虚构内容：

1. **认领贡献（主动语态铁律）**。每条主语是「我」+ 具体动作动词（完成/敲定/推动/判断/筛掉/争取到）。禁无主语句和被动句：「文件收到了」→「我收到文件，待核对完整性」；只有明确记录了核对动作，才能写已核对。禁自我拆台词修饰已完成的事实：「只是/顺带/尝试/大概/我觉得」一律删。
2. **升维三选一**。写条目前先问：这件事里我做了什么**决策**、提了什么**建议**、推动了什么**变化**？能落在三者之一就按那个维度写，纯执行才写「完成」。判断力也是成果——「筛掉了什么、为什么不跟进」值得单独成条。
3. **有可核对数字时再量化**（self-stat）。数量、轮次、时长、覆盖面、时间压缩比（「3 项审阅重点」「10+ 封中筛出 1 条」「当天闭环」），必须可复核；没有证据就不写数字，不猜数量或区间；金额/估值等红线数字除外。
4. **句首放最想被记住的成果词**。读者只记句首——「天使轮二期交割只差纸质件」开头，不要把它藏在句尾当补充。
5. **读者温度排序**。领导当下最关注的主题（从近期日历、群消息、当季节奏推断，如融资季/交割季）排第一条，其次才按自评重要性。明日有相关评审/例会时，今天就把对应成果放进日报——决策窗口前呈现，胜过事后补充。
6. **归功不藏功**。协作事项写「与同事协同推进，我负责的部分是…」；每周至少一次点出同事的具体贡献（不写姓名，按披露规则用角色）。公开致谢让认领自己那部分显得可信而非抢功。
7. **留一个追问钩子**。每天最多一处有余味的下一步或发现（「初评成立的话会给出转介建议」），邀请对话，不做独白。
8. **短板三步法**。延期/问题：一句承认 → 一句通用原因 → 一句已在推进的补救。不辩解、不隐瞒、不渲染。
9. **小步高频，不攒大招**。小进展也当天入报；本目录的日报即个人成就素材库，月度/年终汇总直接从中提取，不再临时回忆。
10. **投入感克制使用**。每周 1-2 处允许真实的第一人称投入表达（「全程盯到当天闭环」），基于真实感受，不表演。

## 4. 范围过滤

只写 `config.work_scope` 内的事项。范围外的（个人学习、副业、私人事务、与岗位无关的活动）**直接省略，不改写包装成工作**。

## 5. 实体披露分级

默认规则（投资机构口径；其他岗位在 setup 时与用户确认等价规则）：

- 被投企业 / 客户公司：默认匿名，写「被投企业例行跟进」「投后信息整理」这类概括表述。
- 正在接触/在看的项目：可保留项目名，除非有特别保密约定。
- LP / 外部个人：写类别（「LP」「外部律师」「候选人」），不写姓名和可识别信息。
- 无法判断归属时按更敏感的一档处理。

**任何情况下不进入日报**：金额、估值、条款、持股、cap table、投资决策、未公开融资/并购/上市、人事法务健康信息、私聊原文、引荐路径、密码/token/内部链接。

## 6. 格式

标题与栏目取自 `config.report`（默认贴合「AI 日记」要求）：

```
【AI日记】2026-09-02（周三）

今日主线
<一句话：今天工作的重心与进展定位，如「两家被投企业的治理与交割事项同步推进，均已进入外部把关/收尾环节」>

今日推进
1. <重点事项：按 §3 叙事公式展开 3-4 句>
2. <重点事项：同上>
3. <次要事项：一句平实陈述，轻量量化>
（3-5 条为宜）

明日计划
1. <取自明天日历与未完成事项，带上目的：「跟进 X，以便 Y」>
（1-3 条）

风险与关注（可选，最多 1 条）
- <真实存在的依赖或风险点，通用表述，如「交割文件原件寄送在途，到件前保持跟踪」>
```

AI 是生成日报的幕后工具，不汇报 AI、Coding Agent、自动化脚本或所用工具，也不设置相关栏目。

## 7. 语气

- 第一人称、平实自信，像认真写给上级看的工作记录；不要公文腔、不要 emoji、不要营销词。
- 量化只用证据支持、可以复核的数字；无法确认数量时省略，不用猜测的区间代替。
- 偶尔一条「阻塞/需要支持」显得真实，但内容要通用（如「等内部反馈」），每周不超过 2 次。
- 周五的「明日计划」写下周；节假日/周末不生成（除非当天真有工作信号）。

## 8. 生成后红线自检（逐条过）

- [ ] 无被投企业/客户名、外部个人姓名、金额、估值、条款、决策、未公开信息
- [ ] 无 `work_scope` 之外的个人事项
- [ ] 每条「完成」都有 §2 的证据支撑
- [ ] **每句演绎都能归到 §3 阶梯的 A/B/C 级，经得起上级追问「具体说说」**——答不上来的句子删掉
- [ ] 无空话堆砌：删掉任何没挂在具体事实上的框架词
- [ ] 今日主线与各条目第一句均为概括句（观点/结果），无「做了 N 件事」式缺乏思想句；措辞明确到可检验
- [ ] 每条主语是「我」+具体动词，无被动/无主语句，无「只是/顺带/尝试/我觉得」类自我拆台词
- [ ] 出现的数字均可复核，没有证据时已省略量化；能升维成「决策/建议/推动的变化」的条目没有写成纯执行
- [ ] 无邮件/聊天原文引用，无内部链接、文件路径、凭据
- [ ] 来源失败时在日报末尾 meta 行注明（如「注：今日邮箱源未连接」），不用旧数据冒充当天事实

## 9. 交付

默认 `delivery: agent_conversation`：保存到 `report.output_dir`，并在设置该 Skill 的 Agent 任务或会话中交付。只有用户明确授权固定外部接收方与发送方式后，才可额外发送；接收方变更需重新确认。
